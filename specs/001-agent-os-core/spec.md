## Clarifications

### Session 2026-09-02

- Q: Agent 的 `notify` 通知推送工具应通过什么方式把消息实际投递出去（例如推送到企业 IM 群）？ → A: 通用 Webhook——向 Agent 配置中声明的 URL 发起 HTTP POST（消息体为文本内容），受域名白名单约束；企业微信/飞书/钉钉群机器人原生支持 incoming Webhook，IM 渠道接入仍在范围外
- Q: 会话在多长时间没有任何新消息后，应当自动结束并归档？ → A: 默认闲置 30 分钟自动归档，超时阈值可按 Agent 配置覆盖；归档不丢数据，历史仍可查询
- Q: 修改 `AGENT.md`、白名单或 Provider 等配置之后，变更应当在什么时机生效？ → A: 重启生效——修改配置后重启服务或新开交互会话生效；核心阶段不实现配置热加载（「运行时切换无锁定」指改配置即可换供应商，非热切换）
- Q: 当用户或业务系统向一个已经归档的会话发送消息时，系统应该怎么处理？ → A: 按渠道区分——交互对话在无活跃会话时自动开启新会话；REST API 向已归档会话发消息返回明确错误并引导创建新会话
- Q: `recall_memory` 按关键词检索长期记忆时，应该采用什么匹配方式来判定「相关内容」？ → A: 包含匹配——查询词（大小写不敏感）在某条记忆内容中出现即命中，返回命中条目/行；语义/向量检索留扩展阶段

### User Story 1 - 与 Agent 对话完成多步任务：ReAct 循环（Priority: P1）🎯 MVP

企业用户（开发者/运维人员）通过初始化工作区、创建一个 Agent 目录（一份含运行配置与任务指令的 `AGENT.md` 文件），无需编写任何代码即可定义一个 Agent。随后通过命令行交互对话（`oryxos chat`），用自然语言给它下达任务：Agent 思考需要做什么、决定调用哪些工具、查看执行结果、再决定下一步，如此往复（Reason → Act → Observe），直到给出最终答复或达到最大迭代次数上限。整个过程循环行为完全可控，全部动作留有结构化日志。

**Why this priority**: 这是 Agent OS 的大脑与最小价值闭环——"自然语言下达任务 → 拆解执行 → 交付结果"。没有它，其余能力（记忆、工具扩展、对外服务）都没有附着点；第一周即可交付可演示成果（多轮对话 + 工具任务）。

**Independent Test**: 可通过"初始化工作区 → 创建 Agent → 启动对话 → 下达一个需要调用工具的多步任务（如查询外部信息并汇总）→ 获得正确最终答复"完整验证，不依赖记忆、扩展工具与 REST 服务即可交付价值。

**Acceptance Scenarios**:

1. **Given** 已初始化的工作区与至少一个已配置模型供应商密钥，**When** 用户执行初始化与 Agent 创建命令并按模板填写 `AGENT.md`，**Then** Agent 目录与运行配置生效，可通过命令行进入与该 Agent 的多轮对话。
2. **Given** 一个处于对话中的 Agent，**When** 用户下达一个需要至少两次工具调用才能完成的任务，**Then** Agent 自主决定调用工具、将执行结果纳入后续推理、继续循环，最终给出综合了工具结果的答复。
3. **Given** 一个任务导致推理循环持续产生工具调用，**When** 达到最大迭代次数上限（默认 10 次，可按 Agent 配置覆盖），**Then** 循环强制终止，系统返回明确的未完成说明而非无限执行。
4. **Given** 同一实例上已定义多个不同配置的 Agent，**When** 用户分别与之对话，**Then** 各 Agent 使用各自的配置与指令独立工作，互不干扰（配置即 Agent、多 Agent 并存）。

### User Story 2 - Agent 能干事：工具体系与安全沙箱（Priority: P2）

Agent 通过工具操作外部世界。开箱即用一组内置工具：文件读取/写入/目录列举、Shell 命令执行、HTTP 请求、长期记忆读写、通知推送。所有工具调用前必须通过应用层白名单校验（文件路径白名单、命令白名单、网络域名白名单）并受执行超时限制，白名单外的操作 100% 被拦截。业务方扩展工具时有三档门槛可选：零代码（写一个 Agent 目录、复用现成的 MCP server）、轻代码（自写 MCP server，任何语言）、重代码（用底座原生方法深度集成），选择原则是"能用低门槛就不用高门槛"。

**Why this priority**: "能干事"是 Agent 区别于聊天机器人的根本；同时企业敢不敢上生产取决于安全隔离与审计。工具体系是第二周的主线交付。

**Independent Test**: 可通过"给 Agent 配置内置工具 → 让其执行文件操作与受控命令/请求 → 验证白名单外操作被拦截 → 以零代码方式接入一个现成 MCP server 并成功调用"独立验证，不依赖记忆与 Web Service。

**Acceptance Scenarios**:

1. **Given** 一个配置了文件、Shell、HTTP 工具的 Agent，**When** 用户要求它读取本地文件并基于内容发起一次外部查询，**Then** 工具按序执行且结果被正确回传给模型用于后续推理。
2. **Given** 工具白名单配置中不包含某路径/命令/域名，**When** Agent 尝试通过工具访问它们，**Then** 调用被 100% 拦截，错误信息回传给模型与用户，不产生实际访问。
3. **Given** 一次工具执行，**When** 执行失败或超时，**Then** 系统按重试策略（指数退避、默认最多三次）重试，仍失败时将失败原因回传给模型继续推理而非中断会话。
4. **Given** 业务方希望接入一个企业自有系统能力，**When** 其仅编写 Agent 目录配置并复用现成 MCP server（零代码档），**Then** 该能力出现在 Agent 可用工具中并可被调用，全程未编写代码。
5. **Given** 一次任意工具调用，**When** 调用发生，**Then** 系统留有一条完整审计记录（工具名、输入、结果、成功与否、耗时），可按会话追溯。

### User Story 3 - Agent 记得住：跨对话记忆（Priority: P2）

用户与 Agent 的对话体验跨会话延续。会话记忆保存当前对话完整历史，按渠道 + 用户 + Agent 联合标识，持久化到本地，底座重启后进行中的会话可恢复；上下文超出模型窗口上限时截断早期对话、保留近期。长期记忆以一个跨对话共享的 Markdown 文件（`MEMORY.md`）承载：Agent 通过两个内置工具主动写入（追加）与按关键词检索，启动时整个文件作为长期上下文注入。用一段时间后，Agent 自然记住用户偏好、项目背景与关键决策，下次对话无需重新解释——这是 Agent OS 区别于 chatbot 的核心体验。

**Why this priority**: 记忆让 Agent 从"一次性应答"变成"越用越懂你"，是产品差异化体验；持久化同时是第四周工程化收尾（会话跨重启恢复）的前置。与工具体系同属第二周主线。

**Independent Test**: 可通过"对话中告知 Agent 一个偏好 → 确认其写入长期记忆 → 开启全新会话询问该偏好 → 验证 Agent 无需重复解释即可正确回答；以及重启底座后恢复进行中会话"独立验证。

**Acceptance Scenarios**:

1. **Given** 用户在对话中说明一个希望长期记住的信息，**When** Agent 调用记忆写入工具，**Then** 内容被追加到长期记忆文件，并在新会话中无需重新告知即可被检索使用。
2. **Given** 一个进行中的多轮会话，**When** 用户重启底座后继续同一会话，**Then** 对话历史完整恢复，Agent 保持上下文连贯。
3. **Given** 会话上下文累计超出模型窗口上限，**When** 用户继续发消息，**Then** 系统截断早期对话、保留近期对话，对话不中断。
4. **Given** 长期记忆文件内容超过设定上限（4000 字），**When** Agent 启动新对话，**Then** 系统按规则截断注入内容，系统不报错。

### User Story 4 - 业务系统接得进来：Web Service 对外服务（Priority: P2）

OryxOS 将全部能力通过 REST API 对外暴露，这是企业业务系统（ERP/CRM/运维平台/告警系统等）接入的唯一通道，任何能发起 HTTP 请求的开发语言都可集成。核心阶段提供 10 个关键端点，覆盖四类能力：会话管理（创建会话、发消息、查历史、归档会话）、Agent 无状态调用、信息查询（Agent/Profile 列表、长期记忆、可用工具）、系统状态（健康检查、运行信息）。同一 Agent 定义无论从命令行、REST API 还是定时任务触发，都走同一条调用链路，行为一致。

**Why this priority**: "对外服务"是 OryxOS 企业级定位区别于个人向 Agent 产品的关键；业务集成都走这条路。为第三周主线交付，且是端到端 Demo（定时触发 + REST 验证）的验收通道。

**Independent Test**: 可通过"启动服务 → 依次调用 10 个端点（创建会话 → 发消息获得回复 → 查历史 → 归档 → 无状态调用 → 查询列表/记忆/工具 → 健康检查/运行信息）"独立验证，全部返回预期结果。

**Acceptance Scenarios**:

1. **Given** 运行中的服务，**When** 业务系统创建会话并连续发送多条消息，**Then** 每次都能获得 Agent 回复，且历史查询端点返回完整对话记录。
2. **Given** 一个短任务场景，**When** 业务系统调用 Agent 无状态调用端点，**Then** 获得一次性结果，不产生需要维护的会话状态。
3. **Given** 同一个 Agent，**When** 分别通过命令行与 REST API 触发同一任务，**Then** 两者行为一致（同一调用链路），且自动触发的会话记录同样可通过历史查询端点追溯。
4. **Given** 到达设定时间点（定时任务触发），**When** 无任何人工干预，**Then** Agent 自动完成一次完整任务循环（如查询天气并推送），全过程可通过审计与会话记录追溯；同时支持人工手动补跑一次做验证。
5. **Given** 监控系统，**When** 调用健康检查与运行信息端点，**Then** 获得可用于探活与运维观测的结构化状态。

### User Story 5 - 模型不锁定：多 Provider 无锁定切换（Priority: P3）

Agent 不感知具体使用哪家模型服务。底座通过统一的 Provider 抽象对接主流大模型，每个 Provider 实例以名称、模型名、密钥（经环境变量注入，绝不明文出现在配置文件或提交记录中）与可选服务地址定义。多个 Provider 并存时以显式映射区分，同一个 Agent 仅修改配置即可在供应商之间切换，运行时切换无锁定。核心阶段至少完整跑通两家主流供应商（如 DeepSeek、Kimi），Provider 故障时直接报错给 Agent（故障转移留待扩展阶段），每次模型调用记录供应商、模型与 token 用量。

**Why this priority**: 它是"运行时切换无 lock-in"这一核心承诺的落点，但前四个 story 已能基于单一供应商交付完整价值；供应商广度与切换能力在其之上增强。属第四周工程化收尾范围。

**Independent Test**: 可通过"为同一 Agent 先后配置两家不同供应商 → 分别完成同一任务 → 再将运行中配置切换到另一家并重复任务 → 三次均成功且审计记录中的供应商/模型/token 用量正确"独立验证。

**Acceptance Scenarios**:

1. **Given** 两个已配置的不同模型供应商（凭据经环境变量注入），**When** 用户将某 Agent 的配置从供应商 A 切换为供应商 B（仅改配置，不改任何代码）并按重启生效机制使其生效，**Then** 该 Agent 使用供应商 B 正常完成对话与工具任务。
2. **Given** 一个配置文件，**When** 其中使用 `${ENV_VAR}` 占位符引用密钥，**Then** 加载时从环境变量解析，配置文件与提交记录中不出现明文密钥；缺失或非法配置给出清晰报错而非静默失败。
3. **Given** 一个已配置的 Provider 发生故障（不可达/鉴权失败），**When** Agent 发起调用，**Then** 系统返回明确的错误信息给 Agent 与用户（核心阶段不做自动故障转移）。
4. **Given** 任意一次模型调用，**When** 调用完成，**Then** 审计记录包含供应商、模型、token 用量与耗时。

---

### Edge Cases

- 上下文超过模型窗口上限时如何处理？→ 简单截断早期对话、保留近期（总结式压缩属扩展阶段）
- 长期记忆文件超过 4000 字时？→ 注入时按规则截断，不报错
- 模型密钥缺失、过期或配置格式非法时？→ 加载阶段基础校验失败，给出清晰、可操作的报错，不静默失败
- 工具操作落在白名单之外（路径/命令/域名）时？→ 100% 拦截，错误回传模型与用户
- 达到最大迭代次数仍未完成任务时？→ 强制终止并明确说明未完成
- 工具执行失败或超时？→ 指数退避最多重试三次，仍失败则将失败信息回传模型
- 会话超时无消息？→ 闲置达到阈值（默认 30 分钟，可按 Agent 配置覆盖）自动归档，历史可查
- 向已归档的会话发消息？→ 交互对话自动开启新会话；REST 返回明确错误，引导创建新会话
- `oryxos init` 重复执行或目标文件已存在？→ 幂等，已有目录与文件一律不覆盖
- 创建重名 Agent 或 `AGENT.md` 配置非法？→ 明确报错，不产生半成品目录
- Provider 不可用？→ 直接报错（核心阶段无 failover）

## Requirements *(mandatory)*

### Functional Requirements

**工作区与 Agent 定义**

- **FR-001**: 系统 MUST 提供工作区初始化能力，创建包含 Agent 目录、公共 Skill 库、产出物、记忆、会话、日志的标准目录结构与三个引导文件（项目级行为说明、Agent 人格、用户偏好），且初始化 MUST 幂等（已存在内容一律不覆盖）。
- **FR-002**: 系统 MUST 支持"一个目录 = 一个 Agent"：Agent 由其目录内的 `AGENT.md` 定义（frontmatter 为运行配置，正文为任务指令），并提供创建/列出/查看/删除 Agent 的管理命令。
- **FR-003**: 系统 MUST 由 `AGENT.md` 的 frontmatter 自动派生运行时配置（绑定 Provider 与模型、可用工具列表、渠道、迭代上限等），不要求用户手写独立配置文件。
- **FR-004**: 系统 MUST 支持同一实例上多个 Agent 并存且互不干扰，各 Agent 使用各自的配置、工具与记忆。
- **FR-005**: 引导文件（项目级行为说明、Agent 人格、用户偏好）与所引用 Skill 的元数据 MUST 在对话时注入系统提示；Skill 正文与附属资源经文件读取按需进入上下文，Skill MUST NOT 作为工具暴露。

**模型接入（Provider）**

- **FR-006**: 系统 MUST 提供 Provider 统一抽象，使 Agent 与业务配置不感知具体模型厂商；至少完整跑通两家主流供应商。
- **FR-007**: 多 Provider 并存 MUST 以显式映射区分；同一 Agent MUST 仅通过修改配置即可切换 Provider，运行时无锁定。
- **FR-008**: 敏感配置（API key 等）MUST 且只能经环境变量注入，配置文件中仅允许 `${ENV_VAR}` 占位；加载时 MUST 做必填项与格式校验，缺失或非法时给出清晰报错。

**推理循环（ReAct）**

- **FR-009**: 系统 MUST 自主实现 Reason → Act → Observe 推理循环：无工具调用则返回最终响应，有工具调用则执行并回填结果继续循环。
- **FR-010**: 循环最大迭代次数 MUST 可配置（默认 10），达到上限 MUST 强制终止并返回明确说明。
- **FR-011**: 工具的执行编排 MUST 由底座统一控制（含白名单校验与审计落库），不得存在绕过编排的工具执行路径。

**工具体系与安全**

- **FR-012**: 系统 MUST 内置以下工具：文件读取、文件写入、目录列举、Shell 执行、HTTP GET、HTTP POST、长期记忆写入、长期记忆检索、通知推送。通知推送 MUST 以通用 Webhook 实现：向该 Agent 配置中声明的 URL 发起 HTTP POST，消息体为文本内容，同样受域名白名单与审计约束；以此覆盖向企业 IM 群机器人推送的场景（IM 渠道接入仍在范围外）。
- **FR-013**: 所有工具调用 MUST 经应用层白名单校验：文件类按路径白名单、Shell 按命令白名单并带超时、HTTP 按域名白名单；白名单外操作 MUST 100% 拦截。
- **FR-014**: 工具执行失败 MUST 按重试策略处理（指数退避，默认最多三次），仍失败则将失败信息回传模型继续推理。
- **FR-015**: 系统 MUST 支持三档工具扩展：零代码（Agent 目录 + 复用现成 MCP server）、轻代码（自写 MCP server，任意语言）、重代码（底座原生方法）；零代码方式 MUST 全程无需编写代码。
- **FR-016**: 系统 MUST 提供 MCP 客户端能力，可连接外部 MCP server 并将其工具纳入 Agent 工具池。

**记忆**

- **FR-017**: 会话记忆 MUST 按渠道 + 用户 + Agent 联合标识，保存完整对话历史，持久化到本地并在重启后可恢复；上下文超限 MUST 截断早期对话保留近期。会话闲置（无新消息）达到超时阈值后 MUST 自动结束并归档，阈值默认 30 分钟、可按 Agent 配置覆盖；归档不丢数据，历史仍可查询。
- **FR-018**: 长期记忆 MUST 以单一 Markdown 文件（`MEMORY.md`）跨对话共享，支持追加写入与关键词检索，启动时注入系统提示，超过 4000 字按规则截断。关键词检索 MUST 采用包含匹配：查询词（大小写不敏感）在记忆内容中出现即命中，返回命中条目/行。

**对外服务与触发**

- **FR-019**: 系统 MUST 提供 REST API 共 10 个端点：会话管理 4 个（创建、发消息、查历史、归档）、Agent 无状态调用 1 个、信息查询 3 个（Agent/Profile 列表、长期记忆、可用工具）、系统状态 2 个（健康检查、运行信息）。
- **FR-020**: 系统 MUST 提供三种运行模式——交互对话（含单条消息模式）、HTTP 服务、多渠道守护进程——且三者共享同一份配置与会话存储。
- **FR-021**: 系统 MUST 提供定时任务触发（第三触发源），到点自动触发 Agent 执行，且与命令行、REST API 复用同一条调用链路，行为一致。
- **FR-022**: 系统 MUST 提供共 12 个命令行命令，覆盖工作区初始化、状态查看、交互对话、服务启动、守护进程、Agent 管理与查询。
- **FR-023**: 命令行 MUST 支持多轮对话及查看工具调用记录。
- **FR-024**: 核心 CLI Channel 之外的消息渠道（企业微信、飞书、钉钉、Slack 等）不在本期范围。

**审计与可观测**

- **FR-025**: 每次模型调用 MUST 记录审计：供应商、模型、token 用量（输入/输出/合计）、耗时、时间。
- **FR-026**: 每次工具调用 MUST 记录审计：工具名、输入、结果、成功与否、错误信息、耗时、时间；审计记录 MUST 可按会话追溯。
- **FR-027**: 所有动作 MUST 落结构化日志。
- **FR-028**: 配置变更（`AGENT.md`、工具白名单、Provider、MCP server 配置）MUST 在重启服务或新开交互会话后生效；核心阶段 MUST NOT 实现配置热加载。
- **FR-029**: 归档会话的后续处理 MUST 按渠道区分：交互对话在无活跃会话时自动开启新会话；REST API 向已归档会话发消息 MUST 返回明确错误并引导创建新会话。

### Key Entities *(include if feature involves data)*

- **Agent（智能体）**: 一个具象的业务智能体，本体是工作区中的一个目录——`AGENT.md`（frontmatter 运行配置 + 正文任务指令）加可选的 Skill 绑定（相对软连接）、脚本与参考资料。
- **Profile（运行配置）**: 由 `AGENT.md` frontmatter 派生的运行时宿主配置，决定 Agent 用哪个 Provider/模型、可用哪些工具、绑定哪个渠道、迭代上限与定时规则。
- **Provider（模型供应商抽象）**: LLM API 服务的统一抽象实例，含名称、模型名、经环境变量注入的密钥、可选服务地址。
- **Session（会话）**: 用户与 Agent 一次对话的上下文容器，按渠道 + 用户 + Agent 联合标识，含对话历史与状态（进行中/已归档），持久化保存。
- **Memory（记忆）**: 会话记忆（Session 内历史）+ 长期记忆（跨对话的单一 `MEMORY.md` 文件）两层；情景记忆为扩展阶段。
- **Tool Invocation（工具调用记录）**: 每次工具调用的审计实体——关联会话、工具名、输入、结果、成功与否、错误、耗时。
- **LLM Call（模型调用记录）**: 每次模型调用的审计实体——关联会话、供应商、模型、token 用量、耗时。
- **Skill（技能）**: 公共知识实体，存于工作区 Skill 库，Agent 通过软连接选择可见集合；仅注入元数据，正文按需读取；不是工具。
- **Channel（渠道）**: Agent 对外的消息入口；本期仅命令行渠道，HTTP 接入归 Web Service。
- **Workspace（工作区）**: 实例工作目录（`.oryxos/`），容纳 Agent 目录、Skill 库、引导文件、记忆、会话、产出物与日志。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户按部署文档可在 30 分钟内完成单节点部署并跑通第一次与 Agent 的对话。
- **SC-002**: 单节点稳定运行 ≥ 10 个 Agent 与 ≥ 100 个并发会话（持续 4 小时无故障）；会话创建 P99 延迟 ≤ 200ms，底座内部转发开销 ≤ 50ms（模型响应时间不计入）。
- **SC-003**: 100% 的模型调用与工具调用具备完整审计记录，可按会话端到端追溯。
- **SC-004**: 同一 Agent 定义不修改任何代码，仅改配置即可在 ≥ 2 家主流模型供应商之间切换并正常完成任务。
- **SC-005**: 业务方通过零代码方式（仅写 Agent 目录 + 配置复用现成 MCP server）接入外部能力，全程编写代码量为 0。
- **SC-006**: 白名单外的路径/命令/域名访问拦截率 100%，且拦截行为有审计可查。
- **SC-007**: 会话跨重启恢复成功：重启后继续对话，历史完整、上下文连贯。
- **SC-008**: 两个每日自动运行的端到端 Demo 到点跑通（无需人工触发）：其一为"每日天气推送"（覆盖模型接入 + ReAct + 内置 HTTP 工具 + 定时触发，推送经通用 Webhook 投递到企业 IM 群机器人），其二为"每日科技日报"（覆盖零代码 Agent 目录 + MCP + 记忆 + 定时触发）；两者合计覆盖全部五大核心能力，且均支持手动补跑并走同一调用链路。
- **SC-009**: 全部 10 个 REST 端点与 12 个命令行命令可用，外部系统仅通过 HTTP 即可完成从创建会话到获取任务结果的完整闭环。

## Assumptions

- 核心阶段假定部署在可信内网环境，REST API 无认证机制（鉴权属扩展阶段）。
- 单机单节点形态；分布式、多副本、跨节点协作属后续阶段。
- 用户已具备至少一家主流模型供应商的有效 API key；主流供应商均通过其对外接口接入。
- 定时触发与手动触发复用同一调用链路，是验收硬条件；两个端到端 Demo 为核心功能发布硬条件。
- 项目主页/文档站点（静态站点）单独交付，不在本规格范围内，可另立 spec。
- 使用者具备基础命令行操作能力；目标用户为企业内开发者、运维与懂业务的非专业程序员。

## Dependencies

- 至少一家主流模型供应商的有效凭据（经环境变量注入）。
- 零代码/轻代码工具扩展依赖现成 MCP server 生态（如 GitHub、Slack、天气类社区 server）。
- 端到端 Demo 依赖可公网访问的天气/新闻类信息源（域名白名单内），以及企业 IM 群机器人的 incoming Webhook 地址（Demo 一推送目标）。

## Out of Scope

- 扩展阶段能力：企业 IM 渠道（企业微信/飞书/钉钉/Slack）、容器级沙箱隔离、认证/RBAC/SSO、流式响应（SSE/WebSocket）、Webhook 触发、Prometheus 指标与完整可观测体系、Provider 故障转移与 hedging、语义/向量记忆检索、记忆自动抽取与压缩、矛盾检测、多租户、A2A 跨节点协作、GraalVM 原生镜像。
- 社区共建功能（见需求文档第 7 章）。
- 项目主页与文档站点（单独交付）。
