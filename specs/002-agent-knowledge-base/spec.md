**Feature Branch**: `002-agent-knowledge-base`

**Status**: Draft

## Clarifications

### Session 2026-09-09

- Q: 知识库的语义检索若通过外部模型服务完成，会把文档内容发送到工作区之外——这与"数据不出域"的私有部署承诺如何取舍？ → A: 允许外部语义服务（与现有 LLM 调用一致），本地模型留作后续档次
- Q: 当管理员完全没有配置语义服务（不是临时故障，而是从未配置）时，知识库应当仍可创建和检索，还是直接拒绝并要求先配置好语义服务？ → A: 语义服务为必需依赖，缺失时创建/摄取/检索点名报错并指引配置；降级仅适用于"已配置但临时不可用"
- Q: 单个知识库和单个工作区的知识库数量，按什么规模档位设计并作为验收边界？ → A: 不设数量硬上限，仅按成功标准的性能预算验收；容量压力场景的测试数据量由计划阶段按预算推导
- Q: 文档增删改后的（重新）摄取，应当由管理员手动触发，还是系统自动监视文档目录并增量摄取？ → A: v1 仅手动触发（管理命令/接口执行摄取），自动文件监视留作后续增强
- Q: SC-002 要求"回答引用正确率 ≥ 90%"，用于验收的问答集规模定为多少条？ → A: 20 条（90% 通过线容错 2 条）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员创建知识库并摄取文档 (Priority: P1)

管理员在工作区中创建一个具名知识库，向其中添加 Markdown 或纯文本文档，
触发摄取后文档内容变为可检索形态；管理员可随时查看知识库状态（文档数、
处理进度、失败原因）。

**Why this priority**: 没有摄取就没有检索——这是全部后续能力的地基，且可独立
演示"资料进得去、状态看得见"。

**Independent Test**: 创建知识库、放入 3 篇文档、执行摄取、查看状态显示全部
就绪即完成验证，交付"文档被有效组织"的价值。

**Acceptance Scenarios**:

1. **Given** 全新工作区，**When** 管理员创建名为 `product-docs` 的知识库，
   **Then** 创建成功且重名创建被明确拒绝。
2. **Given** 知识库 `product-docs` 已存在，**When** 管理员添加 3 篇 Markdown
   文档并执行摄取，**Then** 状态显示 3 篇全部就绪，各文档的分段数可见。
3. **Given** 某文档内容为空或格式不受支持，**When** 摄取执行，**Then** 该文档
   被标记失败并给出原因，其余文档正常就绪，整体摄取不中断。

---

### User Story 2 - 绑定知识库的 Agent 在对话中检索并给出带引用的回答 (Priority: P1)

Agent 在其定义中绑定一个或多个知识库；用户与该 Agent 对话提出知识性问题时，
Agent 在回答过程中检索所绑定的知识库，最终回答附带可核对的来源引用
（知识库名、文档路径、文档内位置）。

**Why this priority**: 这是知识库的核心价值所在——Agent 中心架构下，检索是
Agent 在对话循环中主动调用的能力，回答可信度靠引用保证。

**Independent Test**: 建一个只含某条事实的知识库，绑定一个 Agent 后提问该事实，
回答同时包含该事实与来源引用即完成验证。

**Acceptance Scenarios**:

1. **Given** Agent `assistant` 绑定了知识库 `product-docs`，**When** 用户询问
   该库内可回答的问题，**Then** 回答内容与库内文档一致且附有来源引用。
2. **Given** Agent `assistant` 未绑定任何知识库，**When** 用户询问知识性问题，
   **Then** Agent 不触发知识库检索，行为与无知识库时一致。
3. **Given** Agent 绑定了 `product-docs` 与 `faq` 两个知识库，**When** 检索发生，
   **Then** 两个库的候选内容均可被召回，引用能区分来源库。
4. **Given** 用户问题在库内无相关内容，**When** 检索返回零结果，**Then** Agent
   收到明确的"未找到相关内容"信号并如实告知用户，不得编造引用。

---

### User Story 3 - 文档变更后增量摄取 (Priority: P2)

文档被修改或删除后再次执行摄取时，系统只重新处理发生变化的文档；未变化的
文档不重复处理，已删除文档从检索范围消失。

**Why this priority**: 决定知识库的长期运维成本，但依赖 Story 1 的摄取基础，
且不影响首次跑通。

**Independent Test**: 摄取 5 篇文档后修改其中 1 篇再摄取，状态显示仅 1 篇被
重新处理即完成验证。

**Acceptance Scenarios**:

1. **Given** 5 篇文档已就绪，**When** 修改 1 篇后重新摄取，**Then** 仅该篇被
   重新处理，其余 4 篇状态不变。
2. **Given** 某文档已删除，**When** 重新摄取，**Then** 该文档从知识库移除，
   后续检索不再返回其内容。
3. **Given** 新增 1 篇文档，**When** 重新摄取，**Then** 仅新文档被处理并入列
   检索范围。

---

### User Story 4 - 检索可观测与降级 (Priority: P2)

每次检索调用的关键信息（查询词、结果数、相关性得分、零结果/降级标志、耗时）
被记录到审计存储；外部语义服务不可用时，检索自动降级为仅关键词路继续工作并
明确标注，不中断对话。

**Why this priority**: 质量内功的第一块——没有检索数据就无法评估与演进；降级
保证私有部署在弱依赖下的可用性。

**Independent Test**: 停掉外部语义服务后发起检索，结果仍可返回且审计记录带
降级标志即完成验证。

**Acceptance Scenarios**:

1. **Given** 正常检索若干次，**When** 管理员查看审计记录，**Then** 每次检索
   一条记录，含查询词、结果数、得分与耗时。
2. **Given** 外部语义服务不可用，**When** Agent 检索知识库，**Then** 检索以
   仅关键词方式返回结果并在审计中标注降级。
3. **Given** 某查询无任何命中，**When** 审计被检查，**Then** 该记录带零结果
   标志。

---

### User Story 5 - 知识库结构总览入口 (Priority: P3)

除关键词/语义检索外，Agent 还可调用结构总览能力了解某个知识库"有什么"——
文档清单与章节大纲；管理员亦可通过管理途径查看同一信息。

**Why this priority**: 对齐"摄取侧多形态知识编译"的行业趋势，解决浏览类、
盘点类问题；但检索已覆盖主流程，属增强。

**Independent Test**: 向绑定知识库的 Agent 提问"知识库里有哪些资料"，Agent
调用总览能力并列出文档清单即完成验证。

**Acceptance Scenarios**:

1. **Given** 知识库含 3 篇多章节文档，**When** Agent 调用总览，**Then** 返回
   文档清单及各文档章节大纲。
2. **Given** 空知识库，**When** Agent 调用总览，**Then** 返回空清单而非错误。

---

### User Story 6 - 检索质量评估集 (Priority: P3)

管理员可从审计积累中回填评估集（问题 + 期望来源文档对），运行评估后得到
检索质量报告（如 top-k 命中率、零结果率、引用正确率），作为后续更换或新增
检索组件的验收门禁。

**Why this priority**: 是任何检索升级（重排、换嵌入模型）能被证明"变好了"的
前提；但依赖 Story 4 的数据积累，且不阻塞日常使用。

**Independent Test**: 准备 10 条"问题→期望文档"对并运行评估，得到一份含命中
率数字的报告即完成验证。

**Acceptance Scenarios**:

1. **Given** 10 条评估样例，**When** 运行评估，**Then** 报告给出每条的命中
   情况与整体命中率。
2. **Given** 评估集中某样例的期望文档不存在于知识库，**When** 运行评估，
   **Then** 该样例被明确标记为无效而非计入失败。

---

### Edge Cases

- 知识库被删除但仍被 Agent 绑定时，Agent 检索收到明确的"知识库不存在"反馈，
  对话不崩溃。
- 摄取与检索并发进行时，检索要么看到旧内容要么看到新内容，绝不返回损坏或
  半成品结果。
- 同一内容以不同路径重复添加时，系统按内容识别并正常摄取，不产生检索噪声。
- 超大文档（远超单篇常规体积）摄取时被合理分段处理，不因体积失败。
- 含中文长文与中英混排文档检索时，两路信号均能命中相关内容。
- 嵌入模型身份变更后对旧索引发起检索时，系统明确报错并指引重建，绝不静默
  返回劣质结果。
- 知识库文件被移出工作区或无读取权限时，摄取给出明确的失败原因。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持创建具名知识库；同一工作区内名称唯一，可并存多个知识库
- **FR-002**: 系统 MUST 支持向知识库添加 Markdown 与纯文本文档
- **FR-003**: 系统 MUST 在文档添加后将其处理为可检索形态，并在知识库状态中
  反映每篇文档的处理进度与结果（就绪/失败及失败原因）
- **FR-004**: 系统 MUST 以 Agent 对话循环中可调用工具的形式提供知识库检索能力
- **FR-005**: Agent 定义 MUST 能绑定一个或多个知识库；检索范围仅限所绑定的知识库
- **FR-006**: 检索结果 MUST 携带来源信息（知识库名、文档路径、文档内位置），
  使 Agent 的回答能给出可核对的引用
- **FR-007**: 系统 MUST 将每次检索调用（查询词、结果数、相关性得分、零结果/
  降级标志、耗时）记录到审计存储
- **FR-008**: 系统 MUST 识别文档的修改与删除，且仅重新处理发生变化的文档；
  未变化的文档 MUST NOT 被重复处理
- **FR-009**: 检索 MUST 融合语义与关键词两路信号并合并排序；语义服务为必需
  依赖，未配置时创建/摄取/检索 MUST 点名报错并指引配置（降级仅适用于
  "已配置但临时不可用"，见 FR-010）
- **FR-010**: 配置了重排服务时系统 MUST 对候选结果重排；未配置时 MUST 降级
  继续检索并在审计中标注
- **FR-011**: 系统 MUST 提供知识库结构总览能力（文档清单与章节大纲），供
  Agent 工具调用与管理员查看
- **FR-012**: 知识库原文与全部索引派生数据 MUST 存放在工作区目录内（私有部署、
  数据不出域）
- **FR-013**: 外部模型服务（语义检索、重排）的凭证 MUST 且只能通过环境变量注入
- **FR-014**: 知识库管理操作（创建、添加文档、摄取、删除、状态查询）MUST 同时
  提供命令行与 REST API 两种途径
- **FR-015**: 嵌入模型身份变化后，系统 MUST 拒绝在不兼容的既有索引上继续检索，
  并明确提示重建索引
- **FR-016**: 删除知识库 MUST 同时清除其索引派生数据；已绑定的 Agent 检索时
  MUST 收到明确的"知识库不存在"反馈
- **FR-017**: 系统 MUST 支持定义评估集（问题 + 期望来源文档对）并输出检索质量
  报告（top-k 命中率、零结果率、引用正确率）

### Key Entities *(include if feature involves data)*

- **KnowledgeBase（知识库）**: 具名的文档集合；属性含名称、描述、文档数、
  索引状态、所用的嵌入模型身份；一个工作区可含多个，Agent 按名称绑定
- **KbDocument（库文档）**: 知识库内的一篇文档；属性含库内路径、内容指纹、
  大小、处理状态（待处理/就绪/失败）、分段数、最近处理时间
- **KbChunk（库分段）**: 文档的一个可检索单元；属性含所属文档、正文、文档内
  位置（章节/序号）、语义向量与关键词信号
- **KbRetrievalRecord（检索审计记录）**: 一次检索调用的审计条目；属性含查询词、
  目标知识库、结果数、相关性得分、零结果/降级标志、耗时、发生时间
- **Agent 绑定关系**: Agent 定义中对一个或多个知识库名称的引用（与既有 Skill
  绑定方式同构）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员从创建知识库到 100 篇典型文档（单篇 ≤ 10KB）全部就绪，
  全程 ≤ 10 分钟且失败数为 0
- **SC-002**: 在 20 条样例的验收问答集上，Agent 回答附带正确来源引用的比例
  ≥ 90%（至多错 2 条）
- **SC-003**: 检索请求 P99 ≤ 3 秒返回结果（含外部模型服务往返）
- **SC-004**: 修改 100 篇文档中的 1 篇后重新摄取，被处理文档数恰为 1
- **SC-005**: 任一历史时段的零结果率与降级率可从审计数据直接统计得出
- **SC-006**: 10 个绑定不同知识库的 Agent 并发检索，全程 0 错误且引用不串库
  （每个回答的引用均来自其绑定库）
- **SC-007**: 更换嵌入模型后发起检索，系统明确报错并给出重建索引指引（而非
  静默劣化）

## Assumptions

- 知识库实体对全工作区公有（存放于工作区内统一位置），Agent 通过名称绑定——
  与既有 Skill 的"公共实体 + 按名绑定"模型同构；Agent 私有库不在本期范围
- 本期文档格式限定 Markdown 与纯文本；PDF 等复杂格式需要更重的解析能力，
  留待后续迭代
- 语义检索与重排依赖外部模型服务（可通过 OpenAI 兼容接口访问），凭证走环境
  变量；本地模型部署作为后续扩展档次。"数据不出域"指原文与索引派生数据的
  **存储**不离开工作区；文档内容在**处理**时发送至所选服务属已接受行为
  （与既有 chat 将对话内容发给 LLM 的姿态一致，服务地址可指向私有网关）
- 图谱类检索（知识图谱构建与遍历）明确不在本期范围；若未来查询日志证明存在
  大量全局综合类问题，可作为新的工具入口独立立项
- 多租户与库级权限隔离不在本期范围（私有单租户部署）
- 知识库规模不设数量硬上限（单库文档数、工作区库数均不设限）；规模能力以
  成功标准的性能预算为验收边界，容量压力场景的测试数据量在计划阶段按预算
  推导
- 摄取触发为手动（管理命令/REST 接口执行）；系统自动监视文档目录并自动摄取
  不在本期范围，留作后续增强（FR-008 的增量识别在手动模式下同样成立）
- 重排服务本期为可选组件：架构上保留槽位（FR-010），默认不配置、降级运行
- 检索质量的量化验收（SC-002）依赖 Story 6 的评估集机制先行建立验收问答集
  （规模 20 条起步）；Story 6 自身独立验证所用样例数与此验收规模互不约束
