## 二、Agent Memory 基础理论

### 2.1 为什么 Agent 需要记忆？

LLM 本身是**无状态**的——每次调用都是"初次见面"。记忆系统让 Agent：

| 能力 | 说明 | 示例 |
|------|------|------|
| **上下文延续** | 跨对话记住用户偏好 | "上次你让我用 Python 实现……" |
| **知识积累** | 从对话中提取长期知识 | "公司的代码仓库在 GitHub oryx-labs 组织下" |
| **决策依据** | 基于历史做更好决策 | "这个问题上次用方案 A 解决了" |
| **个性化** | 适应不同用户的工作习惯 | "张工喜欢简洁的输出，李工需要详细步骤" |

### 2.2 记忆分层模型

```
┌──────────────────────────────────────┐
│          会话记忆（Working Memory）    │  ← 当前对话上下文，LLM 上下文窗口内
│          容量：几十轮对话              │
│          存储：内存 / SQLite           │
├──────────────────────────────────────┤
│          长期记忆（Long-term Memory）  │  ← 跨会话保留，Agent 越用越懂你
│          容量：无限                    │
│          存储：文件 / 向量数据库       │
├──────────────────────────────────────┤
│          情景记忆（Episodic Memory）   │  ← 过去的完整执行记录
│          容量：按时间衰减              │  ← 扩展阶段实现
│          存储：SQLite + 向量化         │
└──────────────────────────────────────┘
```

### 2.3 核心操作

```
save_memory(content, scope)
  → 将信息存入长期记忆
  → scope: CORE（核心记忆）/ ARCHIVAL（归档记忆）

recall_memory(query, k=5)
  → 根据查询检索最相关的 k 条记忆
  → 结果注入到 System Prompt
```

## 三、业界方案调研

### 3.1 Mem0 — 智能记忆层

**定位**：为 AI Agent 提供"类人记忆"的托管服务。

**核心特性**：
- 自动从对话中提取和更新记忆
- 向量化存储 + 语义检索
- 支持记忆冲突检测和去重
- Python SDK，需要外部服务

**适用场景**：需要快速集成的 Python 项目，愿意依赖外部服务。

**不适用的场景**：OryxOS 的定位（私有部署，数据不出域）。Mem0 可以作为一种可选的记忆后端，但不能是唯一选择。

### 3.2 MemGPT / Letta — OS 化记忆管理

**定位**：给 LLM 一个"操作系统"，让 LLM 自主管理自己的上下文窗口和记忆。

**核心概念**：
- 虚拟上下文管理（类似 OS 的虚拟内存）
- 主上下文 ↔ 归档上下文的数据交换
- LLM 主动决定"该记什么""该忘什么"

**启示**：OryxOS 可以从中学到"上下文窗口也是记忆的一种"这一观点，但 OryxOS 不做 OS 层面的记忆虚拟化——那属于 ReAct Loop 的 Prompt 管理范畴。

### 3.3 LangChain Memory

**定位**：LangChain 内置的对话记忆工具。

**核心类型**：
- `ConversationBufferMemory` — 全量保存对话
- `ConversationSummaryMemory` — LLM 摘要后保存
- `VectorStoreRetrieverMemory` — 向量检索

**评价**：简单实用，但缺少结构化提取和记忆管理（去重、冲突处理、生命周期）。

### 3.4 知识图谱（Knowledge Graph）

**定位**：用图结构存储实体及其关系。

**核心特点**：
- 节点 = 实体（人、项目、技术栈）
- 边 = 关系（"属于"、"依赖"、"替代"）
- 查询 = 图遍历（"张工参与过哪些项目？"）

**OryxOS 中的应用**：
- 可以作为记忆的一种**组织形式**（非存储引擎）
- 核心阶段：用 Markdown 文件里的 `[[wikilink]]` 模拟简单的图关系
- 扩展阶段：引入 Neo4j 或 NebulaGraph 做真正的知识图谱

### 3.5 方案对比

| 维度 | Mem0 | LangChain | MemGPT | 知识图谱 | OryxOS |
|------|------|-----------|--------|---------|--------|
| 部署 | ☁️ 云服务 | 📦 内嵌 | ☁️ 云服务 | 🖥️ 自建 | 🖥️ 私有 |
| 存储 | 向量DB | 多种 | SQLite+向量 | 图DB | 文件+SQLite+向量 |
| 检索 | 语义 | 关键词/语义 | 语义 | 图查询 | 关键词+语义 |
| 复杂度 | 低 | 低 | 高 | 高 | 低→中 |
| 数据主权 | ❌ | ✅ | ❌ | ✅ | ✅ |

## 四、OryxOS Memory 技术方案

### 4.1 设计目标

1. **数据不出域**：所有记忆存储在企业自己的基础设施
2. **插件化后端**：支持 Markdown / SQLite / Mem0 三种后端，可切换
3. **核心+归档**：区分核心记忆（永久）和归档记忆（随时间衰减）
4. **关联 Agent**：记忆可按 Agent 隔离（每个 Agent 有自己的记忆空间）

### 4.2 架构概览

```
┌────────────────────────────────────────────────┐
│              MemoryService (门面)                │
│  save() / recall() / list() / archive()         │
├────────────────────────────────────────────────┤
│              MemoryBackend (SPI)                 │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│  │ Markdown │  │ SQLite   │  │  Mem0    │      │
│  │ Backend  │  │ Backend  │  │ Backend  │      │
│  │(默认)    │  │          │  │(扩展)    │      │
│  └──────────┘  └──────────┘  └──────────┘      │
└────────────────────────────────────────────────┘
```

### 4.3 配置

```yaml
oryxos:
  memory:
    backend: markdown  # markdown | sqlite | mem0
```

### 4.4 关键设计决策

| # | 决策 | 选择 | 理由 |
|---|------|------|------|
| 1 | 默认后端 | Markdown 文件 | 人类可读，Git 可版本控制，零依赖 |
| 2 | 检索方式 | 关键词 + 可选语义 | 核心阶段用简单方案，扩展阶段加向量检索 |
| 3 | Agent 隔离 | 按 agentId namespace | 每个 Agent 独立的记忆空间，互不干扰 |
| 4 | 归档机制 | 手动归档 + 时间衰减 | 核心记忆不自动删，归档记忆默认保留 30 天 |
